# Design: Rainfall v2 Materialization

## Technical Approach

Close the loop inside the existing outbox consumer instead of adding a second async stage. `ingest_source_scope` gains an optional `db` and writes the `SourceBatch` intervals; `_process_outbox_row` then computes the snapshot from those persisted rows **plus the batch evidence it just received**, and only then writes `status="done"`. Each outbox row is its own transaction — re-locked before its work, isolated by a `SAVEPOINT` so its failure bookkeeping survives, committed as soon as it finishes (decisions 2b/2c) — and one Beat cycle takes a key from 202 to 200.

Materialization is not one-shot. A daily `rainfall.revisit_stale` sweep runs **two stages**. Stage 1 re-enqueues every current-year key so the same pipeline re-runs: it ingests the days that did not exist yet, supersedes the values CHIRPS NRT restated, advances `comparison_end`, and writes a **new** revision that `get_snapshot` then serves (decisions 3c/9). Stage 2 finalizes the years that have rolled over: a key first materialized under the provisional NRT source would otherwise stay provisional forever, because the request fingerprint encodes only `{scope, year}` (service.py:102-107) and the router serves any snapshot hit without ever re-resolving the role (router.py:130-141). Stage 2 selects on the **served snapshot's own provenance**, re-resolves the work through `resolve_missing_work_source` (service.py:47-79) instead of copying the stale `source_id`, and persists the final revision only when it clears the same display policy the router applies (decision 9b).

```
POST /analyses ──fingerprint──> get_snapshot ──hit──> 200 normalize_snapshot
      │ miss
      ▼
queue_missing_analysis (fingerprint stored, cooldown-guarded)
      │  rainfall_outbox(pending)
      ▼
process_outbox (Beat, 60s) ─> per row: claim (FOR UPDATE SKIP LOCKED)  [SAVEPOINT]
      ├─ ingest_source_scope(db) ─> adapter.fetch ─> persist_intervals
      │      ├─ slot absent           ─> INSERT (provider_revision = family)
      │      ├─ slot equal at 6 dp    ─> no-op
      │      └─ slot value changed    ─> INSERT (family+rN)
      │                                  + rainfall_interval_lifecycle(superseded)
      └─ build_analysis(db, row, batch_evidence) ─> compute.build_snapshot
                 intervals_in_window  (non-superseded rows only)
                 INSERT .. ON CONFLICT DO NOTHING
                 rainfall_analysis_revision
      status=done  ──── commit (this row) ────>  next poll serves 200

revisit_stale (Beat, daily 03:30)
  ├─ stage 1 — current-year `done` keys: copy the key, copy the fingerprint
  │     └─ INSERT a fresh rainfall_outbox(pending) ─> the cycle above re-runs
  │            comparison_end advances ⇒ new data_revision ⇒ new revision row
  └─ stage 2 — completed-year keys whose SERVED snapshot is still provisional
        └─ re-resolve role/source (historical / chirps-v3-final), copy the fingerprint
              └─ INSERT rainfall_outbox(pending) ─> build_analysis decides the write:
                     cross-source + policy-available ⇒ final revision written
                                                       ⇒ stage 2 terminates for that key
                     cross-source + policy-suppressed ⇒ nothing written, the NRT snapshot
                                                       stays served, stage 2 retries tomorrow
                     provisional over an incumbent final ⇒ latched, never written
```

Boundary rule kept from the archived design: adapters own providers, `compute.py` is pure (no I/O), `repository.py` owns SQL, `tasks.py` only orchestrates and owns the Session.

## NRT Correction Supersession

**The hole.** `uq_rainfall_interval_revision` (models.py:49-58) encodes the assumption that a value change arrives with a `provider_revision` change. CHIRPS does not honour it: the catalog pins one revision string per `source_id` (`chirps-v3-sat` → `"v3-nrt"`, chirps.py:26-29) and restates the *values* of recent days behind that same string. Combined with decision 3's `ON CONFLICT DO NOTHING`, a re-fetch carrying a corrected value for an existing slot is silently dropped. In-place UPDATE is not a fallback anyone can reach for later: `trg_rainfall_interval_value_immutable` fires `BEFORE UPDATE OR DELETE` and raises `rainfall audit rows are append-only` (lluvia_v2_001_evidence_foundation.py:120-131); the ORM `before_flush` guard (models.py:187-195) is only the polite half of that.

**Mechanism.** A correction is a new row plus a link, never a mutation.

- A slot's first observation keeps the adapter's own revision, e.g. `"v3-nrt"` — the *family*.
- The n-th correction of that slot is a **new row** with `provider_revision = f"{family}+r{n}"`, e.g. `"v3-nrt+r1"`. The suffix makes the row distinct under `uq_rainfall_interval_revision` without touching the existing row.
- `"+r"` is reserved as the correction separator; adapters MUST NOT emit `+` in a `provider_revision` (the live values are `v3-final` and `v3-nrt`, chirps.py:26-29). `revision_family()` and `correction_revision()` are pure helpers in `compute.py`, and `String(128)` (models.py:66) leaves ample room for the suffix.
- The same unit of work appends a `RainfallIntervalLifecycle` row: `interval_value_id` = the superseded row, `superseded_by_id` = the new row, `event_type = "superseded"`, `expires_at = NULL` (models.py:71-81). `"superseded"` is deliberately not `"expired"`: only `event_type='expired'` with a due `expires_at` makes a row deletable by `purge_expired_rainfall_intervals` (lluvia_v2_001_evidence_foundation.py:132-146), so supersession can never turn into a delete. The table carries no foreign key (lluvia_v2_001_evidence_foundation.py:73), so link integrity is the writer's responsibility — hence the `RETURNING`-driven step 3 below.

**Write algorithm** — `persist_intervals` becomes classify-then-append:

1. Read the slots already current for this `source_id`/scope in the fetch window via `intervals_in_window` (which already excludes superseded rows) — one index scan on `ix_rainfall_interval_lookup` (lluvia_v2_001_evidence_foundation.py:150-154).
2. Classify each fetched interval:
   - **absent** → INSERT with the family revision.
   - **equal** → skip. Equality is `round(new, 6) == round(current, 6)`, the *same* rounding `data_revision_for` hashes (decision 3b), so a difference too small to move the content address never creates a row — and never creates a lifecycle row claiming a correction that the disclosure cannot show.
   - **changed** → INSERT the `+rN` row (N = the current row's ordinal + 1, 1 for a first correction) and then, only for the ids `RETURNING` says actually landed, INSERT the matching lifecycle row.
3. Every insert keeps `on_conflict_do_nothing`. Step 1 is a *classification* read, not a get-before-insert: a lost race degrades to a skipped write, never an `IntegrityError` inside the row's transaction.

Two sweeps for the same key cannot normally overlap — `ix_rainfall_outbox_pending_unique` allows one pending row per key (models.py:166-176) and decision 2c re-claims the row before processing it. If they somehow do and both compute `+r1` with different values, the loser's insert is skipped and no lifecycle row is written for it; the next sweep sees `+r1` as current, still disagrees, and writes `+r2`. Convergent, never double-counted, never silently merged.

**Read resolution.** `intervals_in_window` returns the rows for that `source_id`/scope/window with `NOT EXISTS (SELECT 1 FROM rainfall_interval_lifecycle WHERE interval_value_id = rainfall_interval_value.id AND event_type = 'superseded')`, ordered by `interval_start`; the anti-join rides `ix_rainfall_interval_lifecycle_value` (lluvia_v2_001_evidence_foundation.py:84-86). Because supersession is per slot and append-only, the result holds **at most one row per slot**, which is what makes the "no double count" guarantee structural rather than a convention. `build_snapshot` MUST raise on a repeated `interval_start` instead of summing: a broken invariant has to be loud, not a quietly inflated annual total.

**Rejected alternatives.**

| Alternative | Why rejected |
|---|---|
| UPDATE the value in place | Rejected by the database itself (trigger above), and it would erase the provisional value the spec requires to remain auditable. |
| Re-insert every slot on every sweep with a monotonic sequence | Row explosion: 366 slots × one sweep per day ⇒ ~134k rows per key per year to record a handful of corrections. |
| Widen `uq_rainfall_interval_revision` with a `sequence`/`ingested_at` column | Needs a migration that drops and recreates a unique constraint on an evidence table, and buys nothing: it still needs the classification read to know which sequence to write, and it makes duplicate-slot rows *legal by construction* instead of a detectable defect. |
| Delete the superseded row | `purge_expired_rainfall_intervals` is the only sanctioned delete path and is `REVOKE`d from `PUBLIC` (lluvia_v2_001_evidence_foundation.py:147-149). The table is append-only evidence by design. |
| Reconcile duplicates in `compute` instead of at persistence | `compute.py` is pure by the boundary rule, and this moves a double-count risk into every read instead of eliminating it at the single write. |

## Current-Year Revisit Cycle

`revisit_stale` stops being a per-key passthrough and becomes the sweep a Beat entry can actually call. Its current signature demands six keyword arguments (tasks.py:135-153) that no scheduler can supply and no caller in `app/` does; the only test that touches it asserts the registered task *name* (test_ingest_ops.py:81-98) and stays green.

Per run:

1. `current_year = (now or datetime.now(UTC)).year` — the same clock `resolve_missing_work_source` uses to route a request to the daily role (service.py:60-62), reached through the `now` seam declared in Interfaces so tests can cross a year boundary. At the sweep's fixed 03:30 local hour the UTC instant is 06:30 the same day (Argentina is UTC-3 and observes no DST), so the UTC year and the policy calendar year (temporal.py:91-95) cannot disagree; picking the hour is what removes the year-boundary skew.
2. Select the keys, **rotated** (C2 — review-ledger.md "Pre-PR review — PR3"; PR3 review fix round 1): `SELECT * FROM (SELECT DISTINCT ON (source_id, role, scope_kind, scope_id, scope_version, year) … WHERE status = 'done' AND year = :current_year ORDER BY <key>, completed_at DESC) AS candidates ORDER BY completed_at ASC LIMIT :limit` (`MAX_OUTBOX_BATCH`, 50, tasks.py:14; `repository.current_year_done_keys`). `DISTINCT ON` is still mandatory because the sweep itself appends one `done` row per key per day. The OUTER `ORDER BY completed_at ASC` is the fix for what a bare `LIMIT` on the `DISTINCT ON` order would otherwise be: a **monotonically growing set with a deterministic, unrotated prefix cursor**. The `DISTINCT ON` columns are a fixed lexicographic key; without the outer re-sort, the same `limit` keys — whichever sort first — are served every single sweep, and any key sorted past position `limit` once `>= limit` OTHER keys exist is **never selected again**, ever: its `comparison_end` freezes for the rest of the year, silently (this is JDA-001's own bug shape, reintroduced at scale by the very mechanism JDA-001's fix built) — and at scale it is exactly the delta spec's own Cadence requirement failing: "the system MUST re-materialize **every** already-materialized analysis key" (specs/rainfall-analysis/spec.md:35, this change's own delta spec — not the main spec.md:167/238 citations used elsewhere in this document for the unrelated display/eligibility MUSTs). Rotation closes it for free: a key's own successful refresh gives its NEXT `done` row a fresh `completed_at` (step 4 below, once the refreshed row is processed), which is exactly what sends it to the back of the least-recently-attempted-first queue — no separate bookkeeping, no additional column.
3. Skip a key that already has a `pending` row (its refresh is still in flight) or whose newest `done` row has a NULL `request_fingerprint` (the decision-4b legacy shape, which compute cannot address) → `rainfall.revisit.skipped{reason:"pending_in_flight"|"fingerprint_unavailable"}`.
4. INSERT a fresh `pending` row copying the key, `work_labels`, `interval_start/end` and `request_fingerprint` from that newest `done` row, with `retry_count = 0` and `next_attempt_at = now()`. Catch `IntegrityError` on `ix_rainfall_outbox_pending_unique` → rollback and skip, the same discipline decision 8 applies to `queue_missing_analysis`.

**Sweep-level observability (PR3 review fix round 1, merging R4-203 + R2-004).** Each run emits `rainfall.revisit.completed{revisit_scanned, revisit_enqueued, revisit_skipped, truncated}` after stage 1 finishes, where `truncated = (revisit_scanned == MAX_OUTBOX_BATCH)` — the caller's signal that the candidate set may hold more than this run reached, closed by rotation on the next sweep rather than by raising the limit. Stage 1 runs inside its own `try`/`except`: an unexpected exception is recorded as `rainfall.revisit.failed{error_type, error_message}` and stage 2 still runs this cycle (a completed year's transition must not go a day late because stage 1 hit a transient DB error), and the task — `bind=True, max_retries=2` restored on `revisit_stale` after the two-stage rewrite dropped it without an equivalent — retries via Celery's own mechanism once both stages have run and recorded their events.

The refreshed row then rides the normal cycle: `_process_outbox_row` re-fetches the full year (tasks.py:112-113), `persist_intervals` inserts the days that did not exist yet and supersedes the ones CHIRPS restated (decision 3c), and `build_analysis` writes a **new** revision because `data_revision` covers both the resolved interval values and the advanced disclosure window (decision 3b). `get_snapshot` serves newest-first (repository.py:26-33), so the next poll of the *same* fingerprint returns the newer snapshot — the request fingerprint never changes, only the revision behind it does.

**Same-date comparison (spec.md:76-81).** `comparison_end` is recomputed at every build from `temporal.comparison_end(year, buenos_aires_date(now))` (temporal.py:10-11, 91-95) and the baseline from `baseline_dates(comparison_end)` (temporal.py:98-103). One build per day keeps the served comparison end within 24 hours plus one outbox cycle of the calendar, and the selected-year and normal periods always end on the same month and day — which is exactly what the requirement asks and what a frozen snapshot cannot deliver.

**Completed years are exempt from *this* stage.** For a past year `comparison_end` is `date(year, 12, 31)` (temporal.py:11) — constant — and re-running the *same* `source_id` over it recomputes an identical `data_revision`, collides on `uq_rainfall_analysis_snapshot` and writes nothing, after paying for a full-year GEE fetch. The `year = current_year` filter is a quota decision as much as a policy one, and a completed year's last *freshness* refresh is the final stage-1 sweep before the year rolls over.

What the exemption does **not** cover is the provisional→final transition. An earlier version of this design asserted that the transition "is the role switch (past year → historical role → `chirps-v3-final`), which materializes on the next request for that key". **That claim is false and is retracted.** `resolve_missing_work_source` (service.py:47-79) is only reached through `queue_missing_analysis`, and `read_analysis` calls that only on a `get_snapshot` **miss** (router.py:130-141). The fingerprint is a hash of `{scope, year}` and, when present, `event_window` (service.py:102-107) — it carries neither role nor source — so the "next request" for a completed year hits the *same* fingerprint, hits the NRT revision written while the year was still running, and is served from it. The role switch never runs for a key that has already materialized. Stage 2 below is what actually performs the transition.

**Bounds and costs.**

- **GEE**: one full-year zonal fetch per current-year materialized key per day. Narrowing the refetch to a trailing window is the obvious optimization and is deliberately **not** taken here — we have no provider evidence for how far back CHIRPS NRT restates (open question below).
- **Rows**: `rainfall_outbox` grows by one `done` row per current-year key per day (~365/key/year) and `rainfall_analysis_revision` by at most one row per key per day. Both are small and additive; the outbox has no retention job today — tracked, out of scope.
- **Kill switch**: a role gated off by `analisis/rainfall_feature_flags` is skipped, not consumed, by `_process_outbox_batch` (tasks.py:215-225), and `ix_rainfall_outbox_pending_unique` caps the backlog at one pending row per key, so a kill-switched deployment accumulates at most one stale pending row per key. Removing the Beat entry is the sweep's own kill switch.
- **Inert until the flip**: before PR 4, current-year keys route to the daily role and `sqpe-obs` is unwired (tasks.py:66-70), so no current-year key ever reaches `done` and the sweep finds nothing. The machinery ships dark; the flip stays the single step that opens traffic.
- **Rotation bound (PR3 review fix round 1, C2)**: a key sorted past position `limit` is reached within a bounded number of sweeps proportional to `⌈key_count / MAX_OUTBOX_BATCH⌉`, not never — verified against the reproducibility refuter's own repro (51 current-year keys, one sorted lexicographically last, reached on the second sweep once the first sweep's 50 refreshes are processed and rotate to the back).

## Year-Rollover Finalization

**The hole.** A key materialized while its year was still running is served from a `chirps-v3-sat` / `temporal_state="provisional"` snapshot (decision 7). Nothing in the request path ever revisits that: the fingerprint is `{scope, year}` (service.py:102-107), the router serves any `get_snapshot` hit (router.py:130-141), and stage 1 filters the year out the moment it completes. Left alone, the year is served from provisional NRT data permanently — breaking spec.md:167 (a later final revision MUST become visible) and spec.md:238 (historical metrics MUST use CHIRPS v3 Final). Stage 2 is the only path that closes it.

**What "served state" means, and where it is read from.** The single v1 metric is `annual.selected` (decision 5). `MetricResult` pins `temporal_state: Literal["provisional", "final"]` (schemas.py:37) and a frozen, `extra="forbid"` `Provenance` whose first field is `source_id` (schemas.py:11-12, 39); `Provenance` also carries `freshness` and `available_through` (schemas.py:18-19). Those fields are not optional decoration — spec.md:117 requires source class and identifier plus provisional/final state on **every** displayed and exported metric, and decision 5b already forbids omitting any of them. So the persisted snapshot is a complete and self-describing record of which source produced the served answer, which is exactly what stage 2 needs. One pure helper reads it:

```
served_state(snapshot) -> (source_id, temporal_state) | None    # compute.py
```

`None` means the envelope did not disclose it (a corrupt or pre-contract row) and is treated as *unknown*, never as *finalized*.

**Selection algorithm** — per run, after stage 1, with its own `MAX_OUTBOX_BATCH` budget:

1. `current_year` comes from the same `now` seam stage 1 uses (see **Current-Year Revisit Cycle** step 1 for why the 03:30 local hour makes the UTC year and the policy calendar year agree).
2. SQL pre-filter, **now WITH the served-state termination pushed into it** (C1 — review-ledger.md "Pre-PR review — PR3"; PR3 review fix round 1). Base filter: `WHERE status = 'done' AND role = 'daily' AND year < :current_year AND request_fingerprint IS NOT NULL`. `role = 'daily'` is exact rather than heuristic: `resolve_missing_work_source` assigns `role="daily"` **only** when `year == datetime.now(UTC).year` (service.py:60-62), so a `daily` row on a completed year is precisely "materialized while the year was still running". A `historical` row was already final-sourced and needs nothing. `request_fingerprint IS NOT NULL` also makes every legacy row inert — the column does not exist before `lluvia_v2_005`, so all pre-change rows are `NULL` (decision 4b). **Added exclusion**: a lateral read of each candidate's own newest revision (`created_at DESC, id DESC` — the same order `get_snapshot` uses) that already discloses `("chirps-v3-final", "final")`, via `IS NOT TRUE` on the JSON comparison so SQL's three-valued logic KEEPS (does not silently drop) a key whose fingerprint has no revision yet or whose newest revision cannot be read — both read as `NULL`, and only a `TRUE` disclosure excludes. Same query shape as stage 1, but the mechanism that closes the starvation is NOT the same (R4-301, corrected below — "Drain bound, corrected"): `DISTINCT ON (scope_kind, scope_id, scope_version, year) … ORDER BY <scope+year>, completed_at DESC` in an inner query, re-sorted `completed_at ASC` in the outer one, bounded at `MAX_OUTBOX_BATCH` (tasks.py:14; `repository.completed_year_daily_done_keys`). Unlike stage 1, a stage-2 candidate's `completed_at` is never re-stamped — every finalization attempt INSERTs a separate `role='historical'` row (step 6 below) rather than refreshing this one — so the outer re-sort is a static tie-break over whichever candidates the `already_final` exclusion above leaves, not a rotation; it is that exclusion, not the re-sort, that frees a slot for a key parked past the cursor. See "Bounds and costs" → "Drain bound, corrected" for the resulting bound.
3. **Termination — now primarily an SQL exclusion, not a Python branch; the Python read stays as defense-in-depth.** A terminated key is excluded by step 2's own SQL before it ever reaches this loop, relying on the latch (below) guaranteeing a provisional revision is never written over a final incumbent, so "newest revision is final" and "a final revision exists" stay equivalent for as long as that guarantee holds — this reliance is the thing that makes the SQL exclusion sound rather than a heuristic, and it is documented at the point of the query (`repository.completed_year_daily_done_keys`'s own docstring), not asserted here in isolation. For each candidate that DOES reach this loop, read the newest revision with `get_snapshot(db, request_fingerprint)` (repository.py:23-33) and branch on `served_state`:
   - `("chirps-v3-final", "final")` → **terminated** (counted in `rainfall.finalization.completed{finalization_terminated}`, R2-004): the SQL exclusion should already have caught this — reaching it here means a final revision landed in the race window between the SQL scan and this read. Skip this key for this run; the SQL exclusion catches it on the next sweep once its own read is current.
   - any other `(source_id, temporal_state)` → enqueue the transition.
   - revision missing → skip, `rainfall.finalization.skipped{reason:"revision_missing"}` (a `done` row with no revision is the JDA-002 healing case, not a finalization case).
   - `served_state` returns `None` → skip, `rainfall.finalization.skipped{reason:"provenance_unavailable"}`. Loud, not silent.
4. Skip when the **re-resolved** key already has a `pending` row → `rainfall.finalization.skipped{reason:"pending_in_flight"}`.
5. Assert, and skip with `rainfall.finalization.skipped{reason:"event_window_key"}`, when the `done` row's `interval_start`/`interval_end` are not the year bounds. This is **structurally unreachable** rather than merely inert: `resolve_missing_work_source` routes any request carrying an `event_window` to the intensity role before the year test is reached (service.py:57-62), so a `role='daily'` row cannot have event-window bounds. It is kept as a cheap assertion because step 6 re-derives the bounds from the year alone, and a silently mismatched window would be a wrong answer rather than a crash.
6. INSERT a fresh `pending` row whose key fields come from `resolve_missing_work_source(None, year, now=now)` — `source_id="chirps-v3-final"`, `role="historical"`, `interval_start`/`interval_end` at the year bounds (service.py:20, 63-65, 71-72) — and whose `request_fingerprint` is **copied verbatim** from the `done` row. `work_labels` gain `"finalization"` alongside `"role:historical"`. `IntegrityError` → rollback and skip, the same discipline decision 8 applies.
   The `now=now` is not decoration: `resolve_missing_work_source` routes on `year == datetime.now(UTC).year` today (service.py:60) with no clock parameter, so under the design's own simulated-clock test pattern the sweep would select a completed year with its seeded `now` and then re-resolve it against the **real** wall clock — routing it straight back to `daily`/`chirps-v3-sat`, the very state stage 2 exists to leave. Threading the same instant the sweep used for `current_year` is what makes the re-resolution agree with the selection. The seam is declared in Interfaces (`now: datetime | None = None`, `None` → `datetime.now(UTC)`) and touches exactly that one comparison; the interval bounds are derived from `year` alone (service.py:71-72) and are clock-independent.

The split in step 6 is the whole point and is worth naming: **the fingerprint is the identity of the request and MUST NOT change** (it is what `get_snapshot` and therefore the router look up); **the source and role are the work and MUST be re-resolved**, because the `done` row's `source_id` is exactly the stale provisional value we are trying to leave behind.

**Why the outbox-history predicate is wrong.** The obvious selection — "has a `daily` done row but no `historical` done row" — is a trap, and it is the reason step 3 reads the revision instead. CHIRPS v3 Final publishes with months of lag, so the first finalization attempts legitimately fetch data the write gate below refuses to persist. That refused attempt still ends with the outbox row at `done` (decision 1b: a refusal is not a failure — there is nothing to retry). An outbox-history predicate therefore stops selecting the key after the **first** attempt, months before final data is adequate, and the year stays provisional forever while every artifact says the transition ran. Selecting on the served snapshot's provenance has the opposite bias: it keeps trying until an adequate final revision is actually **being served**, which is the only observable that means the MUST has been satisfied. Outbox rows are still useful here — the refusal events give ops the attempt count — but strictly as observability, never as the termination condition.

**Write gate — no-regression semantics.** Applied inside `build_analysis`, on the candidate snapshot, before any INSERT, and under the per-fingerprint advisory lock described in **Serializing siblings** below — which is `build_analysis`'s first database statement, so the incumbent read is already serialized when it runs. It reads the incumbent with the same `get_snapshot` call and classifies:

```
revision_write_decision(incumbent, candidate, policy) -> "write" | "latched" | "gate_refused"    # compute.py
```

- **No incumbent**, or the incumbent's `served_state` is `None` (an envelope the router would 503 on anyway), or **incumbent and candidate name the same `source_id`** → `write`. This is stage 1's daily rebuild and the first-materialization case; decision 3b's content address already makes a no-information rebuild a silent no-op, so no gate is needed and none is applied. Treating an unreadable incumbent as absent is deliberate: a corrupt row must stay replaceable.
- **Cross-source, candidate `provisional`, incumbent `final`** → `latched`. Never write. See the latch below.
- **Cross-source otherwise** (the finalization case) → `write` **iff** `apply_metric_policy(RAINFALL_METRIC_POLICY, "annual", value=…, coverage=…, quality_score=…, completeness=…).state == "available"` (policy.py:148-172); otherwise `gate_refused`.

`policy.py` is pure (dataclasses and arithmetic), so `compute.py` importing `apply_metric_policy` keeps the boundary rule intact — no Session, no network.

The gate is deliberately **not a new threshold**. It is the *same function the disclosure path already runs*: `normalize_snapshot` → `_normalize_metric` → `apply_metric_policy` (service.py:256-263). That equivalence is what makes "no regression" provable rather than asserted — if the candidate would come back `suppressed` on display, persisting it would replace a rendered number with a null carrying `coverage_below_threshold` (policy.py:167) or `quality_below_threshold` (policy.py:169); if it comes back `available` it renders a number backed by final data. Note the exact semantics being borrowed: `apply_metric_policy` compares **both** `coverage` and `completeness` against `minimum_coverage_by_metric[metric]` (policy.py:166) and `quality["score"]` against `minimum_quality_by_metric[metric]` (policy.py:168), and returns `unavailable` when the value is `None` (policy.py:170-171) — all three are refusals here. The thresholds are the module constants of decision 5d; the open question that pins their numbers now has a second consumer, and that is called out there.

**Absolute threshold, not `≥ incumbent`** — chosen deliberately, and the alternative is not merely redundant but *wrong*:

1. The two revisions' `coverage`/`completeness` are ratios over **different windows**. Decision 5c measures them over `[year_start, min(comparison_end, last_interval_end))`. The incumbent NRT revision for a completed year was last built by whichever stage-1 sweep ran while the provider was lagging, so its denominator can end days before 31 December and its completeness can read `1.0` over a *short* window; the finalization build measures the full year and can read `0.99` over a *complete* one. `≥ incumbent` would refuse the strictly better revision, permanently — the exact failure this whole finding is about, reintroduced through the gate.
2. Even with equal windows the comparison is a float knife-edge on two ~`1.0` quantities; a rounding difference produces a permanent refusal with no diagnosis.
3. `apply_metric_policy` is the only definition of "good enough to show" that exists in this system. Inventing a second, relative one means two disagreeing notions of adequacy, and the display path wins anyway.

**The latch — why the stage-1 year filter does not compose on its own.** Stage 1 never *enqueues* a daily row for a completed year, but that is not the same as no daily-role build ever landing on one. Two live paths cross the boundary: a stage-1 row enqueued on 31 December and still `pending` (or backing off, tasks.py:179-181) when the worker drains it in January; and a user request for year Y made minutes before midnight, which `resolve_missing_work_source` routes to `daily` at *request* time (service.py:60-62). Either one produces a `chirps-v3-sat` build for a completed year. Its `data_revision` differs from the final one (`source_id` is inside the address, decision 3b), so it would write a new row, and `get_snapshot`'s newest-first order would serve the **provisional** revision over the final one — silently undoing the transition and violating spec.md:176-181 ("subsequent retrieval identifies the result as final"). The `latched` branch is what prevents it, and it costs nothing extra: it reads the incumbent the gate already read. Refusals are recorded as `rainfall.build.latched`. The branch is a decision *rule*; what makes it a *guarantee* under the overlapping runs decision 2c calls "the norm" is the lock below.

**Serializing siblings — the per-fingerprint advisory lock.** `revision_write_decision` reads the incumbent through a plain, non-locking `get_snapshot` (repository.py:23-33), so on its own the latch is only as good as the order the two builds happen to read in. And the two builds are reachable by construction: a finalization row (`historical`/`chirps-v3-final`) and a daily row (`daily`/`chirps-v3-sat`) for the same `request_fingerprint` are **different outbox keys**, so `ix_rainfall_outbox_pending_unique` (models.py:166-176) admits both as `pending` at once, and `process_outbox` runs every minute while a batch takes far longer (celery_app.py:154-158, decision 2c), so two workers can claim them concurrently — `FOR UPDATE SKIP LOCKED` keeps them off each other's *rows*, not off each other's *fingerprint*. If the daily sibling reads the incumbent before the finalization sibling commits and commits after it, `revision_write_decision` sees no final incumbent, returns `write`, and its provisional revision wins `created_at DESC` (repository.py:29-31) — shadowing the finalized year, exactly what the latch exists to forbid.

The fix is to make read-decide-insert atomic per fingerprint. As its **first** database statement — inside the per-row transaction of decision 2c, before the incumbent read — `build_analysis` takes a transaction-scoped advisory lock keyed on the fingerprint:

```sql
SELECT pg_advisory_xact_lock(:lock_key)
```

The key derivation is exact and needs no new column, because the fingerprint already **is** a lowercase sha256 hex digest (`hashlib.sha256(canonical.encode()).hexdigest()`, service.py:102-107): take its first 16 hex characters — the first 8 bytes — read them as an unsigned big-endian 64-bit integer, and reinterpret that as PostgreSQL's signed `bigint`.

```python
def fingerprint_lock_key(request_fingerprint: str) -> int:   # compute.py, pure
    unsigned = int(request_fingerprint[:16], 16)
    return unsigned - (1 << 64) if unsigned >= (1 << 63) else unsigned
```

Deterministic across workers and processes (no `hash()` randomization), and a collision between two unrelated fingerprints costs one shared queue slot, never a wrong answer. A row with a `NULL` fingerprint (decision 4b) skips compute entirely and therefore never takes the lock. The raw statement lives in `repository.py` per the boundary rule (design.md:42) as `acquire_fingerprint_lock`; `build_analysis` calls it.

`pg_advisory_xact_lock` — not the session-level `pg_advisory_lock` — is the shape decision 2c needs: it is released automatically when the row's own transaction commits or rolls back, with no explicit unlock and nothing to leak if the worker dies mid-row. A session-level lock would outlive the row and would have to be released by hand on every exit path, including the failure paths decision 2b exists to keep writable.

What it buys, stated as the sequence: the second sibling **blocks** on the lock until the first sibling's transaction *commits*, then reads a **fresh** incumbent and decides against it. A daily build arriving after a finalization commit now sees the final incumbent and returns `latched`; a finalization build arriving after a daily one gates against the incumbent that actually exists. The interleaving that produced the shadowing is no longer expressible.

Interaction with decision 2b's savepoint, stated exactly rather than hand-waved: the lock is taken inside the row's `SAVEPOINT`, and so is everything it guards (incumbent read → decision → INSERT). On the success path the savepoint is *released*, its locks pass to the enclosing transaction, and the advisory lock is therefore held until the per-row COMMIT — which is precisely what a waiting sibling needs, since the INSERT only becomes visible to it at that commit. On the failure path the savepoint is *rolled back*, which drops the lock early; that is harmless, because the same rollback discarded the INSERT, so the sibling that acquires the lock next reads an incumbent this attempt did not change. Either way, no sibling ever observes a half-finished decision.

**Why it cannot deadlock.** Each build acquires exactly **one** advisory lock, never nests a second one inside it, and gives it up only by ending its transaction — so there is no lock-ordering cycle available to construct. The only other lock the transaction holds is the `FOR UPDATE SKIP LOCKED` claim on its *own* outbox row (decision 2c), and `SKIP LOCKED` means no worker ever *waits* on another worker's row lock. The single blocking wait in the entire path is the advisory lock, and whoever holds it is waiting on nothing the waiter holds.

**Ordering, once written.** `get_snapshot` orders `created_at DESC, id DESC` (repository.py:29-31) and `created_at` is `server_default=func.now()` (models.py:98-100), so the finalization revision — written strictly later, in its own transaction (decision 2c) — sorts first and is served with no further coordination. That argument now rests on the **lock**, not on timing: the lock is what makes "strictly later" a fact instead of a hope, because two builds sharing a fingerprint cannot interleave their read-decide-insert sequences at all, so a provisional build that runs after a finalization commit is `latched` and never writes a row for the ordering to have to sort correctly. The `id DESC` tiebreak is a random-UUID order and would be arbitrary, but a tie needs two revisions for one fingerprint sharing a `now()` value; `now()` is transaction-start time in PostgreSQL, one build writes at most one revision, and the lock serializes the only two builds that could share a fingerprint. Not a live ordering risk.

**Termination, stated as a proof obligation.** Stage 2 stops selecting key K if and only if `get_snapshot(K.fingerprint)` returns a snapshot whose `served_state` is `("chirps-v3-final", "final")`. That snapshot exists only if `revision_write_decision` returned `write` for a final-source candidate, which happens only when the gate passed. Therefore no refused attempt can extinguish the sweep, and no sequence of refused attempts can either — which is the property the outbox-history predicate fails to have. **This paragraph specified the proof obligation from the start; it did not specify WHERE it is enforced, and an earlier version of this design incorrectly stated that step 2's SQL pre-filter already enforced it (it did not — the pre-filter had no served-state awareness at all, and termination lived entirely in step 3's Python `continue`, past a `LIMIT` with no rotation, which does not bound how long a terminated key keeps being re-scanned once other keys sort ahead of it).** PR3 review fix round 1 (C1) closes that gap by moving the enforcement into step 2's own SQL, exactly as this paragraph's proof already required — the SQL exclusion is the mechanism, step 3's per-row read is the defense-in-depth for the documented race window, and the proof obligation itself is unchanged. Delta spec: specs/rainfall-analysis/spec.md:69, this change's own delta requirement ("Once an adequate final-source revision has been written and is served, the sweep MUST stop enqueueing transitions for that key") — not the main spec.md:167/238 citations used elsewhere in this document for the unrelated display/eligibility MUSTs.

**Bounds and costs.**

- **GEE**: one full-year zonal fetch per *stalled* completed-year key per day, on top of stage 1's one per current-year key per day. The stalled set drains to empty once CHIRPS v3 Final publishes an adequate year, and steady-state cost is zero. Stage 2 has its own `MAX_OUTBOX_BATCH` budget, evaluated after stage 1, so a backlog of stalled finalizations can never starve the daily refresh.
- **No backoff in v1**, deliberately. (a) The cost is already bounded at one fetch per key per day and the key set is the handful of zone/basin scopes staff actually analyze. (b) The right backoff constant is a function of CHIRPS v3 Final's publication lag, which is exactly the provider evidence the design already records as an open question — picking a number now would be the same unevidenced guess the design refuses to make about narrowing the refetch window. (c) A backoff delays a MUST-visible transition (spec.md:167) to save an amount of quota nobody has measured. Instead every refusal emits `rainfall.finalization.gate_refused{scope, year, coverage, completeness, quality_score}`, so the first real deployment produces the evidence a backoff would need. Adding one later is a scheduling change, not a redesign.
- **Rows**: one `done` outbox row per stalled key per day and zero revision rows while the gate refuses — a refused attempt is cheaper on storage than a successful one.
- **Kill switch**: removing the `rainfall-revisit-stale` Beat entry stops stage 2 along with stage 1; the latch lives in `build_analysis` and stays active regardless, which is the correct asymmetry (stopping the sweep must not re-open the downgrade path).
- **Inert until the flip**: before PR 4 no current-year key can reach `done` (the daily role points at the unwired `sqpe-obs`, tasks.py:66-70), so no `role='daily'` `done` row with a non-`NULL` fingerprint can exist and stage 2's pre-filter matches nothing. The prod rows that exist today (1 `done`, 2 `failed`) all predate `lluvia_v2_005` and therefore have `request_fingerprint IS NULL`.
- **Drain bound, corrected (R4-301 — review-ledger.md "PR3 scoped re-review (fix round 1)")**: the outer `completed_at ASC` re-sort is NOT a rotation the way stage 1's is. A stage-2 candidate's `completed_at` never changes — it is the original `role='daily'` `done` row, and every finalization attempt INSERTs a separate `role='historical'` row (step 6 above) that never re-stamps it — so the relative order of the keys that remain candidates is fixed for as long as they stay candidates. What frees a slot for a key parked past the `MAX_OUTBOX_BATCH` cursor is the `already_final` SQL exclusion alone: once an ahead-of-cursor key's served state genuinely turns final, it drops OUT of the candidate set entirely, shrinking the population the cursor has to clear. With up to `MAX_OUTBOX_BATCH` genuinely-stalled keys sorted ahead of a given key, draining the head takes at most `ceil(N / MAX_OUTBOX_BATCH)` daily sweeps, where N is the count of ahead-of-cursor keys that eventually clear the write gate — a key stuck behind a head that never clears (inadequate final data that never improves) is not bounded by this arithmetic and stays starved until that data improves. Observable via `rainfall.finalization.completed`'s `truncated` flag (`scanned == MAX_OUTBOX_BATCH`); a persistently `true` value is the signal the head has not drained.
- **Observability (merges R4-203 + R2-004)**: `rainfall.finalization.completed{finalization_scanned, finalization_enqueued, finalization_skipped, finalization_terminated, truncated}` fires every run; `finalization_scanned == finalization_enqueued + finalization_skipped + finalization_terminated` always closes, and `finalization_terminated` is normally zero in steady state (the SQL exclusion, not this counter, does the real work) — a persistently nonzero value is itself a signal the SQL exclusion and the latch have drifted out of the agreement this design relies on.

| Alternative | Why rejected |
|---|---|
| "The role switch handles it" (the previous claim) | Unreachable for a materialized key: `queue_missing_analysis` runs only on a `get_snapshot` miss (router.py:130-141) and the fingerprint carries no role (service.py:102-107). Retracted above. |
| Select on outbox history ("`daily` done, no `historical` done") | Self-extinguishes on the first gated-but-refused attempt, months before CHIRPS Final is adequate — the year stays provisional forever while the audit trail looks complete. |
| Copy `source_id`/`role` from the newest `done` row (stage 1's step 4) | Re-fetches `chirps-v3-sat` and rewrites the provisional answer. Copying the *fingerprint* is required; copying the *work* is the bug. |
| Gate on `≥ incumbent` completeness/coverage | Compares ratios measured over different windows (decision 5c) and can permanently refuse a strictly better final revision; also a float knife-edge on two near-`1.0` values. |
| Sweep completed years through stage 1's freshness path | Same `source_id` ⇒ identical `data_revision` ⇒ collides on `uq_rainfall_analysis_snapshot` and writes nothing, after paying a full-year fetch. Freshness and finalization are different problems with different termination conditions. |
| Widen the request fingerprint to include role/source | Changes the identity of every existing request, orphaning every stored revision, and would still not re-resolve anything for a key already in cache. |
| Backoff after N refusals in v1 | Needs the provider-lag evidence the open questions already flag as missing; instrumented instead. |
