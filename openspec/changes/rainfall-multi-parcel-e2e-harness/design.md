# Design: Deterministic Multi-Parcel Rainfall E2E Harness

## Design Status

**Implementable.** The current repository provides every production contract needed by
RMEH-001..014 without a production seam: URL camera navigation, ordinary MapLibre parcel
clicks, a real `tipo=parcela` ficha request, stable ficha selection keys, `Lluvia` tab
continuity, body-scroll reset, offline test authentication, and network-boundary rainfall
fixtures. The missing pieces are test infrastructure only.

The production-code forecast remains **0 lines**. If implementation discovers that any
production route, prop, store export, MapLibre exposure, test ID, or behavior is required,
implementation MUST stop and escalate; that is a design failure, not permission to widen
scope.

## Technical Approach

Add one fail-closed, operator-invoked harness around the existing rainfall Playwright file:

1. A Python runner creates a cryptographically unique Compose project, database name,
   loopback ports, evidence directory, ownership marker, and local `ResourceLease`. The lease
   exists before provisioning and can authorize teardown only for the exact Docker resources
   this invocation creates; it never authorizes database mutation. The runner accepts no
   caller-supplied database URL.
2. A dedicated test Compose file provisions a new PostGIS volume and only the services the
   journey needs: Postgres, Redis, migration runner, backend, Martin, and frontend.
3. After database ownership is proven, the runner applies repository migrations, inspects the
   provenance and shape of both required materialized views, seeds exactly three real-derived
   parcel geometries (A/B/C) plus the preserved legacy parcel `3603003210041000` that the ten
   pre-existing rainfall tests click (a fourth real-derived row; the pre-existing tests resolve
   it by `nomenclatura` through the real ficha endpoint), plus one deterministic covering
   soil/zone fixture from one committed
   GeoJSON, creates or
   refreshes only a provenance-permitted `vt_parcelas_catastro`, refreshes the migration-owned
   `mv_suelos_por_zona`, and validates every hard postcondition.
4. A fixture-aware Playwright helper validates deterministic rainfall contracts, derives
   parcel click targets from committed camera states using Web Mercator, validates canvas
   and occlusion geometry, and confirms each plain click through the real ficha request and
   rendered identity.
5. One additional Playwright test executes mobile and desktop A -> B -> C -> A state machines
   in separate browser contexts. The existing ten rainfall tests remain intact, producing
   exactly **11 passed, 0 failed, 0 skipped**.
6. The runner classifies bootstrap failures separately from product assertion failures,
   always tears down only run-owned resources, retains non-secret evidence, and emits a
   separate JDA-001 handoff candidate without modifying the parent review record.

```text
operator / workflow_dispatch
          |
          v
Python lifecycle runner -----> evidence/<run-id>/events.jsonl
          |
          +-- local resource lease --> unique Compose project + fresh volume
          |                                |
          |                                `-- DB marker gate --> OwnedBoundary
          |
          +-- migrations --> fixture seed --> provenance-gated views --> services
          |                                                          postconditions
          |
          +-- Playwright collect gate (exactly 11)
          |
          +-- Chromium rainfall suite
          |       +-- existing 10 tests
          |       `-- one multi-context mobile+desktop transition test
          |
          `-- teardown --> residual-resource check --> manifest.json
```

## Safety Boundary and Threat Model

### Threat

The primary P0 threat is accidental mutation or deletion of a developer, shared, staging,
or production database when a self-healing command is pointed at the wrong target. Secondary
threats are cleaning another concurrent run, exposing credentials in artifacts, and reporting
a green run after partial setup.

### Identity Model

For each invocation the runner generates:

```text
run_id          = 128-bit random lowercase hex
compose_project = rmeh-<run_id-prefix>
database_name   = rmeh_<run_id-prefix>
marker_nonce    = independent 256-bit random hex
resource_lease  = independent local lease id bound to run_id and exact Docker identities
evidence_dir    = .artifacts/rainfall-multi-parcel/<run_id>/
host origins    = http://127.0.0.1:<generated app/api/martin ports>
```

The runner does **not** accept `DATABASE_URL`, database host, database name, Compose project,
or cleanup target overrides. The only optional inputs are evidence location, keep-evidence
policy, and workflow/local presentation settings. Every published port binds to
`127.0.0.1`; `0.0.0.0`, non-loopback hosts, default database name `consorcio`, fixed Compose
project names, and pre-existing target resources are rejected.

### Provisioning Gate Before Bootstrap Writes

Provisioning and bootstrap are separate phases:

1. Before provisioning, create a local `ResourceLease` and write `ownership.json` with run
   identity, exact planned Compose/container/network/volume names, and mode `lease-planned`.
   The lease grants no SQL/DDL/DML capability.
2. Render `docker compose config` with generated values and verify the resolved service
   database URLs, labels, project name, volume, network, and loopback port bindings.
3. Inspect Docker by exact generated names and labels. Any pre-existing container, network,
   or volume is an identity collision and aborts. The runner never adopts it, records no
   created resource in the lease, and therefore has no authority to delete it.
4. Provision the stack. After each resource appears, inspect its immutable Docker ID, exact
   name, Compose project label, run label, and lease label, then append that identity to the
   flushed lease manifest. Mount a generated mode-0600 init script into the brand-new Postgres
   volume. The first
   database initialization creates `rmeh_ownership(run_id, marker_nonce, database_name)`.
   This provisioning write is safe because the volume was proved absent and is labelled for
   this run before Postgres starts.
5. Query the marker read-only through `docker compose exec`, checking all three values plus
   `current_database()` and the internal endpoint `postgres:5432`.
6. Only after those checks construct the in-memory `OwnedBoundary`, set `ownership.json` to
   `database-owned`, and permit migrations/seed DDL. Marker query error, absence, or mismatch
   never constructs this token.

Absent marker, mismatched nonce, unexpected database name, non-loopback publication,
pre-existing resource, or label disagreement exits with `BOOTSTRAP_SAFETY_FAILURE` before
migrations or fixture writes. Every database-mutating runner method requires an in-memory
`OwnedBoundary` token that only the successful marker gate can construct; unit tests use a
recording command adapter to prove unsafe paths issue zero database-mutating commands.

Cleanup uses the separate `ResourceLease`, including when marker query/validation fails before
an `OwnedBoundary` exists. It can target a recorded immutable ID or reconcile an exact predeclared
name only when that resource carries this invocation's exact cryptographic lease, run, and Compose
project labels; this closes interruption between Docker creation and manifest append without
adopting a collision. Before deletion it records/rechecks the immutable ID and refuses every label
mismatch. It never searches by prefix, uses the DB token for Docker teardown, or issues a global
Docker prune. Resource absence after exact leased teardown is a postcondition; residual leased
resources turn an otherwise passing run red without granting database writes.

## Bootstrap and Hard Postconditions

Bootstrap is bounded and self-healing only inside `OwnedBoundary`.

### Ordered Plan

1. **Database identity** — re-read `rmeh_ownership`; abort on mismatch.
2. **Migrations and relation inspection** — run `alembic upgrade head`; validate Alembic head,
   `parcelas_catastro`, `suelos_catastro`, `zonas_operativas`, PostGIS, geometry types, SRID 4326,
   required indexes/columns, and classify both named materialized-view relation slots as absent
   or present with inspected provenance/shape. Before any relation drop/recreate, inspect
   `pg_namespace`, `pg_class.relkind`, PostgreSQL owner, `obj_description`, columns/types,
   indexes, and the defining query digest.
3. **One bounded disposable rebuild** — if migration state, a migration-owned table, or
   migration-owned `mv_suelos_por_zona` is absent/incompatible, or an existing migration/unknown
   `vt_parcelas_catastro` is incompatible, recreate only the run-owned database in the same fresh
   cluster, reinstall/revalidate the marker, rerun repository migrations once, and repeat the
   complete relation inspection. The rebuild budget is global and exactly one. A remaining
   mismatch aborts explicitly; the runner never hand-creates a migration-owned object.
4. **Fixture seed transaction** — validate fixture first, then replace data in the run-owned
   `parcelas_catastro`, `suelos_catastro`, and `zonas_operativas` tables with deterministic rows.
   Parcel UUIDs and nomenclatures are stable. The soil and one synthetic fixture zone use valid
   SRID-4326 `MULTIPOLYGON`s covering A/B/C, giving the soil view one deterministic positive-area
   zone/soil intersection.
5. **Martin projection provenance gate** — use the relation state classified in steps 2-3. If
   `public.vt_parcelas_catastro` is absent after migrations, create it as a materialized view
   with `geometria` plus the seven public Martin
   properties and stamp the exact harness run/lease ownership comment. If it carries that exact
   marker, the harness may drop/recreate and refresh it. If it is migration-owned or has unknown
   provenance, never relabel, drop, or replace it: require compatible materialized-view kind,
   schema, column set/types, defining projection, and row behavior, then use/refresh it without
   changing provenance. Incompatibility consumes the one rebuild in step 3 if still available;
   a post-rebuild mismatch is an explicit drift failure.
6. **Migration-owned soil view** — require `public.mv_suelos_por_zona` after migrations as
   `relkind='m'` with the repository-owned columns (`mv_id`, `zona_id`, `zona_nombre`, `cuenca`,
   `cap`, `simbolo`, `ip`, `ha_suelo`), unique `mv_id` index, expected definition digest, and
   existing ownership/comment unchanged. After fixture seed, refresh it through its supported
   migration-owned contract and require deterministic rows for the covering fixture zone/soil.
   Absence or incompatibility takes only the bounded rebuild path in step 3; the harness never
   creates or redefines this view ad hoc.
7. **Database postconditions** — independently query counts, identities, validity, SRID,
   pairwise non-overlap, soil coverage, materialized-view shape/count, and ownership comment.
8. **Martin** — start the dedicated catalog, require health, require exactly the expected
   `parcelas_catastro` source, request fixture-covering z/x/y tiles, and require HTTP 200,
   vector-tile content type, and non-zero body for each target area. HTTP 204 is empty and fails.
9. **Backend** — start with `FICHA_ENABLED=true`, generated database URL, rate limiting disabled,
   no real GEE credential, and explicit loopback CORS origin. Require `/live`, then POST the real
   ficha request for A/B/C and require successful `tipo=parcela` results. This proves the flag is
   effective rather than merely present in an environment dump.
10. **Frontend** — start with exact generated `VITE_API_URL` and `VITE_MARTIN_URL`; require an
    HTTP-successful `/mapa?lat=...&lng=...&zoom=...` response from the loopback origin.
11. **Rainfall fixture contracts** — run the same pure TS validator used by the route helper;
    require three complete ready contracts and distinct effective query/cache identities.
12. **Idempotency probe** — execute seed/view refresh and all validations a second time in the
    same owned database. IDs, facts, geometry digests, counts, source catalog, and aliases must
    be byte-for-byte/cardinality stable before Playwright starts.

## Fixture Model

`rainfall-multi-parcel.fixture.json` is the sole source for Python seed and TypeScript browser
logic. It is parsed from `unknown` through explicit type guards; no `any` and no direct union
types are introduced. Runtime value sets use `as const` before type extraction.

```typescript
const PARCEL_ALIAS = { A: 'A', B: 'B', C: 'C' } as const;
type ParcelAlias = (typeof PARCEL_ALIAS)[keyof typeof PARCEL_ALIAS];

interface FixtureProvenance {
  sourcePath: string;
  sourceFeatureId: string;
  sourceGeometrySha256: string;
  derivation: 'exact-ring-extraction';
}

interface FixtureRainfallFacts {
  scopeKind: 'zone' | 'basin';
  scopeId: string;
  scopeVersion: string;
  effectiveCacheKey: string;
  percentile: number;
  accumulationMm: number;
  analysisRevisionId: string;
  dataRevision: string;
  metricRevision: string;
}

interface ParcelFixture {
  alias: ParcelAlias;
  stableUuid: string;
  nomenclature: string;
  displayIdentity: string;
  geometry: GeoJsonPolygon;
  interiorPoint: LngLat;
  provenance: FixtureProvenance;
  rainfall: FixtureRainfallFacts;
}
```

### Geometry and Identity

- Extract three nearby, non-overlapping polygon rings from
  `consorcio-web/public/data/catastro_rural_cu.geojson` once during implementation.
- Commit only those rings plus source feature identifiers and canonical geometry SHA-256.
  The harness fixture remains stable if the upstream public asset later changes; drift is a
  diagnostic requiring deliberate fixture review, never an automatic rewrite.
- Replace operational properties with deterministic synthetic values (`RMEH-PARCEL-A/B/C`,
  stable UUIDs, synthetic account/designation). No real operator identity is retained.
- Select an interior point by maximum edge clearance, not centroid assumption. At each
  camera/viewport, the projected point must retain at least 12 CSS px edge clearance.
- Define a 6 CSS px radius clickable disk around each point. Every disk must remain inside
  exactly one projected polygon and must not overlap another parcel's projected polygon or
  clickable disk.

### Controlled Rainfall Facts

The committed fixture uses deliberately separated values, for example:

| Alias | Scope | Percentile | Accumulation | Analysis/metric revision |
|---|---|---:|---:|---|
| A | `zone:rmeh-zone-a:v1` | 21 | 111.1 mm | `rmeh-rev-a` |
| B | `zone:rmeh-zone-b:v2` | 52 | 222.2 mm | `rmeh-rev-b` |
| C | `zone:rmeh-zone-c:v3` | 83 | 333.3 mm | `rmeh-rev-c` |

The effective analysis key is declared and recomputed as
`rainfall-analysis:<kind>:<id>:<version>:<year>`. Scope resolution is keyed by exact
nomenclature. Analysis and series handlers map only from declared scope/revision values; an
unknown identity fails the route instead of falling back to A. Every body is ready and carries
the matching scope, percentile, accumulation, analysis revision, data revision, and metric
revision. There is no queued/error normalization in this new scenario and no GEE request.

## Camera and Projection Algorithm

Each viewport has a committed camera `{lat,lng,zoom}` chosen so all three clickable disks are
inside the unobstructed map region after the `medio` sheet opens. Navigation always uses
`/mapa?lat=<lat>&lng=<lng>&zoom=<zoom>`.

### Projection

For tile size 512 and zoom `z`, all world and canvas values below are CSS pixels. The live
canvas rectangle comes from `canvas.getBoundingClientRect()` after settlement:

```text
worldSize = 512 * 2^z
x(lng) = (lng + 180) / 360 * worldSize
y(lat) = (0.5 - ln((1 + sin(lat)) / (1 - sin(lat))) / (4*pi)) * worldSize

rect = canvas.getBoundingClientRect()
localCssX = rect.width  / 2 + shortestWrappedDeltaX(pointX, cameraX)
localCssY = rect.height / 2 + (pointY - cameraY)
pageCssX = rect.left + localCssX
pageCssY = rect.top  + localCssY
```

Latitude is clamped to Web Mercator's +/-85.05112878 degrees. The helper projects every
polygon ring and interior point, then runs point-in-polygon, edge-clearance, disk-containment,
pairwise ambiguity, clipping, and occlusion checks.

`canvas.click({ position })` receives `{x: localCssX, y: localCssY}`; DOM hit-testing receives
`{x: pageCssX, y: pageCssY}`. Playwright and `elementFromPoint` therefore use the same CSS-space
units and live rectangle offsets. `devicePixelRatio` and backing-store size may be recorded only
as diagnostics; neither is an input to projection, centering, offsets, clipping, or click
coordinates. Deterministic unit probes run the same camera/rectangle fixture at DPR 1 and DPR 2
and require byte-identical local/page CSS coordinates and integrity outcomes.

### Observable Settlement

No scale label, `networkidle`, or arbitrary sleep is a settle criterion. Before every intended
click in a context:

1. Require the map workspace and visible `.maplibregl-canvas`.
2. Parse the URL marker's rendered CSS transform and require its anchor to converge to the
   canvas center for three consecutive animation frames within 1 CSS px.
3. Require the visible compass transform to be identity (zero bearing and pitch), because the
   independent projection supports the production default flat camera only.
4. Require stable canvas bounds for the same three frames.
5. Observe a non-empty `parcelas_catastro` tile at the expected zoom for this camera.

If any condition fails within the bounded 20-second settle budget, attach camera, marker,
compass, canvas CSS rectangle, DPR diagnostic, and tile diagnostics and stop. Frame sampling and
target recomputation may repeat inside this budget, but they emit no pointer interaction.

### Occlusion and Plain-Click Proof

Immediately before every click:

- recompute local/page CSS targets from the live canvas rectangle;
- repeat projected polygon/disk integrity checks;
- require `document.elementFromPoint(pageCssX, pageCssY)` to resolve to the canvas;
- require the point outside the live ficha sheet, marker/popup, navigation/fullscreen/scale
  controls, and any visible element with pointer interception;
- arm exact request observers, then call
  `canvas.click({ position: {x: localCssX, y: localCssY} })` once with no `force`.

Camera settlement, tile observation, projection, and occlusion probes may resample before the
interaction deadline. Once observers are armed, each intended selection has exactly one helper
interaction attempt and exactly one plain click. No second click exists. If the click emits no
ficha request, emits a wrong parcel or `tipo=parcelas`, or renders a missing/wrong identity, the
transition fails immediately with the pre-click geometry, camera, occlusion, request, and render
diagnostics. Playwright test retries are `0`; helper interaction retries are also `0`. The
manifest records attempt count `1` for each of the eight intended mobile/desktop selections.

Success requires all of the following after the click:

1. the real ficha POST body is exactly `{tipo:'parcela', nomenclatura:<target>}`;
2. the rendered parcel identity is the target;
3. a new scope-resolution request carries the target nomenclature;
4. a new analysis request uses the target's exact distinct scope/cache identity;
5. the ready response sequence number is newer than the prior target's;
6. rendered scope, percentile, accumulation, and technical revision match the target.

This outcome confirmation detects projection/model drift without exposing MapLibre internals.

## Browser State Machines

### Shared Ready Assertion

`assertTargetReady(target, previous)` requires:

- `Lluvia` label remains selected;
- ficha identity equals the target nomenclature/display identity;
- the answer card shows the target scope sentence, percentile, and accumulation;
- expanding the existing technical fold shows the target metric revision;
- the latest scope/analysis/series traces belong to the target and are newer than `previous`;
- all five target dimensions differ from `previous` and no previous-only value is current;
- the current rainfall request Authorization header equals the active synthetic token and the
  token appears in no URL.

The technical fold may be expanded to observe revision, but geometry is measured on the
complete collapsed ready answer card. The helper collapses/rechecks before accepting card
containment.

```text
  -> independently prove scrollHeight > clientHeight and scrollTop > 0 again
  -> plain-click A
  -> READY_A2 from a newer A response + no stale C/aliased A cache
  -> Lluvia + scrollTop=0 + complete-card containment
```

For **each** transition, the wheel delta is derived from
`scrollHeight - clientHeight`; direct `scrollTop` assignment, `scrollIntoView`, and keyboard
shortcuts are forbidden. The precondition is sampled immediately before the click and attached
as `{range, beforeScrollTop, afterWheelScrollTop}`. After readiness, require exact zero and the
full card box inside the visible sheet-body box with the existing +/-1 CSS px layout tolerance.

Fresh A on the final transition is not inferred from eventual A text. It requires a new A scope
request and ready response sequence after C, A's exact revision/facts, and the absence of every
C-only fact from the current surfaces.

### Desktop

Use the declared desktop viewport and its committed camera:

```text
plain-click A -> activate Lluvia -> READY_A
plain-click B -> READY_B + stable focus
plain-click C -> READY_C + stable focus
plain-click A -> READY_A2 + newer response + stable focus
```

Before each click, capture the active element. After readiness, focus must be `body`, the canvas,
or the same visible map interaction ancestor. A non-body active element must intersect the
viewport and must not be hidden, inert, disabled, mobile-only, or unrelated. No sheet height,
card containment, body scroll range, or scroll-reset assertion is made on desktop.

## Fail-Closed Test Accounting

The dedicated Playwright config selects only `rainfall-v2-detail.spec.ts`, Chromium, one worker,
and zero retries. The runner performs two machine-readable gates:

1. **Collection gate** — run Playwright collection with JSON output before browser execution;
   require exactly 11 discovered tests. Zero, ten, twelve, omitted file, `.only`, and collection
   errors fail as `HARNESS_ACCOUNTING_FAILURE`.
2. **Result gate** — parse the JSON reporter and interaction evidence after execution; require
   11 expected passes, zero unexpected failures, zero skipped/interrupted tests, zero flaky or
   Playwright-retried tests, helper retry count `0`, exactly eight intended selection records,
   attempt count `1` and click count `1` in each, and the expected project/file identity.

Current soft-gate helpers may still express environmental skips for ordinary runs, but the
owned harness preflight makes those prerequisites mandatory and the final zero-skip gate makes
any residual soft skip red. The runner never translates a missing prerequisite into a test
annotation.

Failure classes are exclusive and preserved in `manifest.json`:

| Class | Meaning |
|---|---|
| `BOOTSTRAP_SAFETY_FAILURE` | Ownership/host/port/marker mismatch; no bootstrap writes permitted |
| `BOOTSTRAP_PREREQUISITE_FAILURE` | Owned stack could not satisfy a hard database/service/fixture postcondition; browser not started |
| `HARNESS_ACCOUNTING_FAILURE` | Discovery/result count, skip, retry, reporter, or evidence contract failed |
| `BROWSER_INTEGRITY_FAILURE` | Browser started, but bounded pre-click camera settlement, CSS projection, clipping, target uniqueness, tile, or occlusion integrity failed before pointer input |
| `PRODUCT_ASSERTION_FAILURE` | All pre-click integrity conditions passed and the single real click occurred, but request, identity, continuity, freshness, scroll, geometry, or focus behavior failed |
| `CLEANUP_FAILURE` | One or more exact run-owned resources remain; overrides an otherwise passing result |
| `PASSED` | All postconditions, 11 tests, evidence, and cleanup passed |

## Local Runner Lifecycle and Evidence

The runner uses an explicit phase enum and one top-level `try/finally`. SIGINT and SIGTERM set a
cancellation phase, forward termination to the active child process group, and enter the same
cleanup path as normal failure. A second signal shortens waits but never changes the cleanup
target.

```text
CREATED -> LEASE_PLANNED -> PROVISIONING -> DATABASE_OWNED -> BOOTSTRAPPED
               |              | marker error          |
               |              `-----------------------+
               |                                      v
               +-- any error/signal ------------> LEASE_CLEANUP -> CLEANED
DATABASE_OWNED -> PREFLIGHT_PASSED -> TESTS_FINISHED -> EVIDENCE_SEALED
       `-- any error/signal ------------------------------------> LEASE_CLEANUP
```

```python
lease = ResourceLease.plan(unique_run_identity)  # Docker teardown only; no DB writes
owned: OwnedBoundary | None = None
try:
    assert_no_resource_collision(lease)
    provision_and_record_each_created_resource(lease)
    owned = validate_database_marker_read_only(lease)  # sole OwnedBoundary constructor
    bootstrap_database(owned)
    run_browser_harness()
finally:
    reconcile_then_teardown_exact_leased_resources(lease)  # valid when owned is None
```

Evidence directory contents:

```text
.artifacts/rainfall-multi-parcel/<run-id>/
├── ownership.json
├── events.jsonl
├── bootstrap.json
├── projection-mobile.json
├── projection-desktop.json
├── request-trace.json
├── playwright-results.json
├── test-results/                 # screenshots/trace only when produced
├── manifest.json                 # final status, counts, digests, cleanup result
└── jda-001-handoff.json          # emitted only for a complete pass
```

The event stream is append-only and flushed after each phase so cancellation still leaves an
explanation. The final manifest includes repository SHA, fixture digest, run/lease identity,
exact created-resource identities, service origins, bootstrap postconditions, 11/0/0 accounting,
Playwright retry count `0`, helper retry count `0`, eight one-click attempt records, evidence
SHA-256s, failure class, and cleanup result.

The generated database password and marker nonce are kept in a mode-0600 temporary environment
file and removed in cleanup. Logs are captured through a redactor that removes password/token
values and authorization/cookie headers. Browser auth uses fixed synthetic non-secret tokens;
traces therefore contain no real credential or PII. Passing traces need not be retained; JSON
geometry/request evidence is sufficient.

## Antithesize Report

### Core Claim

A test-only Python lifecycle runner plus a TypeScript projection/browser helper can satisfy all
46 scenarios and produce production-honest A -> B -> C -> A evidence with zero production-code
changes.

### Counter-Argument

The harness duplicates part of MapLibre's camera model and provisions a substantial disposable
stack. A small production-supported parcel-selection deep link or exposed projection API would
be simpler and less brittle, while a real rainfall backend would be more representative than
route fixtures. The test-only implementation is also much larger than the initial estimate and
could become an unmaintained parallel platform.

### Evidence Against

| Evidence | Source | Strength |
|---|---|---|
| The live map instance is private, so independent projection can drift | Existing `MapaMapLibre` ref boundary | Strong |
| The URL camera uses animated `flyTo`, not a synchronous camera set | `useReportHighlight.ts:69-77` | Strong |
| Base Compose contains fixed shared names and ports, making casual reuse unsafe | `docker-compose.yml:7-17,87-90,347-376,449-469` | Strong |
| Real rainfall/GEE would make fixture outcomes non-deterministic and violates scope | Authoritative proposal/spec | Strong |

### Confidence Impact

**Level: Moderate.** The counter wins if the marker/compass/tile observations cannot make the
flat camera deterministic, or if no real-derived three-polygon fixture stays unobstructed at
both viewports. It does not justify a production hook: either condition blocks this change.

### Steel-Man Rebuttal

The production seam would make the product carry test architecture and would no longer prove the
current operator path. This design confines duplication to a pure, heavily tested formula,
cross-checks it with observable camera DOM/tile/request/render outcomes, and deletes the entire
platform cleanly on rollback. Rainfall route fixtures are already the repository's accepted E2E
boundary and preserve the real cache/render/auth path while excluding GEE by contract.

### Verdict

**Modify and proceed.** Keep the test-only architecture, but treat observable camera convergence,
fixture safe-region proof, and the 1,800-line task forecast as hard continuation gates. Never add
a production seam to rescue a failed gate.
