# audit-2026-10-rag-activo-rotation

Closes audit finding **WARNING RAG-3**: `rag_ingest` upserted `rag_corpus` with `activo=true` and nothing anywhere rotated `rag_corpus.activo`, so after ingest A then B both stayed activo forever while serving resolved `ORDER BY ingested_at DESC` (`app/domains/conocimiento/repository.py`, `CORPUS_ACTIVO_SQL`). "Roll back by re-ingesting A" was a silent no-op for serving — A's `ingested_at` stayed older (it was not in the `ON CONFLICT` update set either) — and the run exited 0 printing `committed:true`. The runbook's only rollback was hand-written SQL `UPDATE rag_corpus SET activo=false` (docs/rag/runbook-encendido.md, step 6 and the "Rollback" paragraph: "set the flag to `false`, or set `activo=false` on the bad row").

Branch: `feature/audit-rag3-activo-rotation` off `origin/main` `14256df5`.

## In

- [x] Rotation inside the ingest transaction: `repository.upsert_corpus` now runs `DEACTIVATE_OTHER_CORPUS_SQL` (`UPDATE rag_corpus SET activo=false WHERE activo IS TRUE AND corpus_sha != :corpus_sha`) immediately after the row upsert, only when `activo=True`. `rag_ingest.ingest` already runs `upsert_corpus` inside its single `session.begin()` transaction, so activation and rotation commit or roll back together. Placement rationale: `upsert_corpus` is the only write path to `rag_corpus.activo`, so the invariant "to activate a corpus is to retire every other one" lives with the write; a separate rotate step called from `ingest()` would be one forgotten call away from the same bug. Re-ingesting the sha that is already active is a no-op rotation-wise: the UPDATE excludes `corpus_sha`, so the row never fights itself.
- [x] `ingested_at` IS refreshed on conflict (`ingested_at = now()` added to `UPSERT_CORPUS_SQL`'s update set). Deliberate decision, commented in the SQL: serving resolves ties with `ORDER BY ingested_at DESC, corpus_sha` precisely because `activo` is not unique in the schema, so a re-ingested snapshot must also become the most-recently-ingested one or the defensive ordering contradicts the rotation ("rollback by re-ingesting A" would reactivate A while the fallback ordering still prefers B). It also keeps the norms badge (`leer_corpus_activo`) reporting a landing time this code actually produced. The corpus idempotency contract is untouched: `test_idempotent_rerun_same_sha` projects `rag_unidad` rows only, which carry no timestamp.
- [x] `scripts/rag_ingest.py` prints the served sha after commit: `main()` resolves `repository.corpus_activo(session)` inside the same commit transaction and prints `served sha : <sha>` in the summary, only for committed runs. A rollback-by-re-ingest that did not move serving is now visible on the console as a `corpus_sha` / `served sha` disagreement instead of a bare `committed:true`.
- [x] Tests `tests/new/conocimiento/test_rag_corpus_rotation.py` (synthetic fixtures, `db` fixture, no `RAG_CORPUS_PATH`, no pgvector marker): (a) ingest A then B leaves exactly one activo row (B), A activo=false; (b) re-ingest A retires B — the rollback scenario, seeded with explicit `ingested_at` values because the `db` fixture's single rolled-back transaction makes Postgres `now()` constant and the serving tie-break would otherwise mask the bug; (c) idempotent re-ingest of the active sha rotates nothing; (d) re-ingest refreshes `ingested_at`; plus two `main()` wiring tests for the served-sha print (committed prints it, dry-run does not).
- [x] RED-CHECK against unfixed code (`git stash` of the two source files, test file left in place): 5 of 6 tests failed — (a), (b), (c), (d) and the committed-print test. A direct probe on unfixed code reproduced the audit claim verbatim: seed A(t1, activo) + B(t2>t1, activo), re-ingest A → `corpus_activo` still returns B. `test_uncommitted_run_prints_no_served_sha` passes on unfixed code by construction (the line does not exist there); it guards the new print, it is not a red target.
- [x] `tests/new/conocimiento/test_normas_eval.py`: the `_SesionFalsa` / `_Sesion` fake sessions grew an `execute` answering the one SELECT `main()` now makes after a committed ingest (served-sha read). Test infrastructure update, not an assertion change.
- [x] Secondary effect from the finding resolved by the primary fix: `scripts/rag_load_vectors.py` preflights `activo IS TRUE` on its target row; with rotation, "activo" means "the row serving resolves", so vectors can no longer load into a stale "active" snapshot serving never reads.

## Out

- No schema changes (no partial unique index on `activo`, no new migration) — the defensive `ORDER BY` in `CORPUS_ACTIVO_SQL` stays and now agrees with rotation.
- No new endpoints, no change to `corpus_activo` / `leer_corpus_activo` / the norms badge.
- No change to `rag_load_vectors.py` itself.
- No change to the runbook's manual rollback (`activo=false` on the bad row remains valid and still yields `sin_corpus_activo` 503 when it is the only active row).
- Corpus-marked (`-m corpus`) full-ingest tests: not run here (no `RAG_CORPUS_PATH` on this box run); they skip in CI by design.
